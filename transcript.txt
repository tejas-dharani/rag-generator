⏺ The brief is short and leaves a lot open. Here's what it asks for and how I'd
  approach it.

  What they're asking for

  1. Accept documents at runtime: users upload files through the app. The files
     aren't baked into the code.
  2. Create a RAG app over those documents: each document set becomes its own
     knowledge base you can ask questions of. This is the "generator" part.
  3. Grounded answers: answers come only from the uploaded docs, cite their
     sources, and say "I don't know" when the docs don't cover the question.
  4. Different document sets without code changes: new documents mean a new
     upload, not new code.

  They're also grading how you work with the AI agent, since the transcript is
  part of the submission. Keep this session going and run /export at the end.

  Recommended architecture

  Upload (PDF/DOCX/MD/TXT/HTML)
     → Parse → Chunk (~800 tokens, with overlap, keep page/section metadata)
     → Embed → Store in a per-collection vector index
  Question
     → Hybrid retrieval (vector + BM25 keyword) → Rerank top-k
     → LLM answers from the retrieved context only, with [citations]
     → Says it can't answer if the context doesn't support an answer

  Stack: Python and FastAPI for the backend, a small web UI (plain HTML/JS or
  Streamlit), ChromaDB for vectors (runs locally, no infra needed), and Claude
  to generate the answers. One command starts everything, e.g. docker compose up
  or make run.

  What makes it a "generator" and not just a chatbot:
  - Collections: each upload creates a named RAG instance with its own index,
    its own chat page (/c/<id>) and its own API endpoint. Several can exist side
    by side.
  - Config per collection: chunk size, top-k and model are set when the
    collection is created, not in code.

  Extras that will stand out to reviewers:
  - Inline citations that link to the source chunk or page
  - Answers stream as they're generated
  - A small evaluation script: a few question/answer pairs per sample doc set
    that check retrieval hit rate and whether answers are grounded
  - Tests, a clear README with architecture notes and trade-offs, and sample
    documents to demo with

  Suggested build order

  1. Scaffold the project, config and README
  2. Ingestion: parsing and chunking, with tests
  3. Embeddings, the vector store and collections
  4. Retrieval, then generation with citations and refusal
  5. API and UI
  6. Eval script, Docker setup, final README

  I can start building this now if you're happy with the plan. One thing to
  confirm first: which LLM/embedding provider do you have an API key for? I'd
  suggest Anthropic (Claude) for the answers plus a local embedding model
  (sentence-transformers), so you only need one key. OpenAI or a fully local
  setup with Ollama would also work.

⏺ You should never put your API key on GitHub. Anyone who can see the repo can
  use it, and bots scan GitHub for leaked keys within minutes. The usual setup
  is: the code goes on GitHub, and each person supplies their own key.

  How it works

  1. Your key lives in a local .env file that git ignores.
  # .env  (stays on your machine, never committed)
  ANTHROPIC_API_KEY=sk-ant-xxxxx
  Your .gitignore already has a .env line (line 151), so git will never commit
  that file.

  2. You commit a .env.example template with no real values.
  # .env.example  (committed to GitHub)
  ANTHROPIC_API_KEY=your-key-here

  3. The code reads the key from the environment, e.g.
  os.getenv("ANTHROPIC_API_KEY"), so no key is ever written in the code.

  How the reviewer verifies your project

  The README tells them to do this:
  git clone <your-repo>
  cp .env.example .env        # then paste their own API key
  docker compose up           # or: make run
  # open http://localhost:8000, upload a doc, ask a question
  Reviewers of this kind of assessment expect this and will normally use their
  own key.

  Ways to make it easier for them

  - A mode that needs no key: use local embeddings, plus an option to run the
    LLM locally with Ollama. The reviewer can then test everything for free with
    no key at all.
  - Tests that don't call the API: the LLM is faked in tests, so pytest passes
    without a key.
  - A demo GIF or screenshots in the README: the reviewer can see it working
    before they run anything.
  - A live demo (optional): deploy to something like Render, Railway or Hugging
    Face Spaces and add your key in that platform's secret settings, where it
    stays hidden. Put a spending limit on the key first.

  The build will include .env.example, the local-model option, tests that don't
  need a key, and a README with these setup steps. Should I start building?

⏺ I checked your Mac: it has 16 GB RAM, an Intel i7 processor (not Apple
  Silicon) and 297 GB of free disk space. Ollama isn't installed yet.

  Size

  The Ollama app itself is small. Each model is a separate download, and bigger
  models give better answers:

  ┌──────────┬──────────┬──────────┬────────────────────────────────────────┐
  │  Model   │ Download │   RAM    │         Answer quality for RAG         │
  │   size   │          │  needed  │                                        │
  ├──────────┼──────────┼──────────┼────────────────────────────────────────┤
  │ 1–3B     │ ~1–2 GB  │ ~4 GB    │ Weak. Often ignores the instructions   │
  │          │          │          │ or makes things up                     │
  ├──────────┼──────────┼──────────┼────────────────────────────────────────┤
  │ 7–8B     │ ~4–5 GB  │ ~8 GB    │ Decent. The best fit for your 16 GB    │
  ├──────────┼──────────┼──────────┼────────────────────────────────────────┤
  │ 14B      │ ~9 GB    │ ~12+ GB  │ Good, but very slow on your machine    │
  ├──────────┼──────────┼──────────┼────────────────────────────────────────┤
  │ 30B+     │ 18+ GB   │ 24+ GB   │ Won't run well on your machine         │
  └──────────┴──────────┴──────────┴────────────────────────────────────────┘

  Browse the model list at ollama.com/library. The Llama, Qwen, Gemma and
  Mistral families all come in the 7–8B range.

  Will it give proper answers?

  - Simple factual questions ("what is the refund policy?"): yes, a 7–8B model
    handles these well, because the retrieval step already gives it the right
    text.
  - Harder cases are noticeably weaker than Claude: citing sources reliably,
    saying "I don't know" instead of guessing, combining facts from several
    documents, and long documents.
  - Speed is the real problem on your Mac. Intel Macs can't use the GPU for
    Ollama, so everything runs on the CPU. Expect roughly 20–60 seconds per 
    answer with a 7–8B model. That's fine for testing but slow for a demo.

  Recommendation

  - Default: Claude through the API. Answers are fast and good quality, and
    that's what you demo and record.
  - Optional: Ollama as a fallback, switched with one setting
    (LLM_PROVIDER=ollama). This shows reviewers the app doesn't depend on one
    provider, and they can run it without a key.
  - Embeddings run locally in both modes. The embedding model is only about 100
    MB and fast even on your CPU.

  You don't need to install Ollama unless you want to test that fallback
  yourself. Should I start building with this setup?

❯ which embedding model we will use                                             

⏺ I recommend BAAI/bge-small-en-v1.5, run locally with the FastEmbed library.

  Why this one

  - Small and fast: about 130 MB, and it runs well on your Intel CPU with no
    GPU. Indexing a 100-page PDF should take seconds to a minute.
  - Good retrieval quality for its size: clearly better than the older, commonly
    used all-MiniLM-L6-v2 at about the same speed.
  - Free and offline: no API key and no cost, and the reviewer gets exactly the
    same results as you.
  - Light install: FastEmbed runs models through ONNX, so you don't need
    PyTorch. That avoids a download of roughly 1 GB or more and keeps the Docker
    image small.

  Alternatives, switchable with one setting

  ┌──────────────────────────────┬────────────┬────────────────────────────┐
  │            Model             │    Size    │        When to use         │
  ├──────────────────────────────┼────────────┼────────────────────────────┤
  │ bge-small-en-v1.5 (default)  │ ~130 MB    │ English docs, fast, good   │
  │                              │            │ enough                     │
  ├──────────────────────────────┼────────────┼────────────────────────────┤
  │ bge-base-en-v1.5             │ ~440 MB    │ A bit more accurate, about │
  │                              │            │  3× slower on CPU          │
  ├──────────────────────────────┼────────────┼────────────────────────────┤
  │ multilingual-e5-small /      │ ~470 MB /  │ Documents not in English   │
  │ -base                        │ ~1.1 GB    │ (Hindi, etc.)              │
  ├──────────────────────────────┼────────────┼────────────────────────────┤
  │ Voyage AI or OpenAI          │ none       │ Best quality, but needs    │
  │ embeddings (API)             │            │ another API key            │
  └──────────────────────────────┴────────────┴────────────────────────────┘

  Why a small model is enough here

  The retrieval pipeline covers for most of what a small model misses:
  1. Hybrid search: vector search finds text with the same meaning, and BM25
     keyword search catches exact terms like names, codes and numbers, which
     small embedding models often miss.
  2. Reranking: a small reranker model (about 80 MB, also local) re-scores the
     top ~20 chunks and keeps the best 5 for the LLM.

  The embedding model name will go in the config (EMBEDDING_MODEL=...), so you
  can switch it without changing code. One caveat: each collection records which
  model it was indexed with, because you can't mix embeddings from different
  models in one index. Changing the model means re-indexing that collection.

  Are your documents mainly English, or do you need multilingual support? If
  they're English, I'll start building with this setup.

  Which OpenAI model

  A "mini" model is the best fit for RAG. The retrieved text already contains
  the answer, so the model mainly needs to follow instructions and cite sources,
  and mini models do that well and cheaply. Something like gpt-4.1-mini or a
  newer mini model should cost a fraction of a cent per question. OpenAI
  releases new models often, so check the model list in your OpenAI dashboard
  and use the newest mini model. Changing it is just an edit to LLM_MODEL.

  Design change: one client that works with several providers

  Ollama also accepts requests in OpenAI's API format, so a single OpenAI client
  covers both:

  ┌──────────────────┬────────────────────────────────────────────────┐
  │   LLM_PROVIDER   │            What the reviewer needs             │
  ├──────────────────┼────────────────────────────────────────────────┤
  │ openai (default) │ Their own OpenAI key                           │
  ├──────────────────┼────────────────────────────────────────────────┤
  │ ollama           │ Nothing but Ollama running locally, fully free │
  ├──────────────────┼────────────────────────────────────────────────┤
  │ anthropic        │ A Claude key (optional adapter)                │
  └──────────────────┴────────────────────────────────────────────────┘

  Embeddings

  I'd still keep local bge-small-en-v1.5 as the default. It's free, works
  offline, and means the reviewer only needs one key. OpenAI's
  text-embedding-3-small will be available as an option
  (EMBEDDING_PROVIDER=openai) if you want higher-quality embeddings. They're
  very cheap, but reviewers without an OpenAI key couldn't use them.

  Final stack

  - Backend: Python + FastAPI
  - LLM: OpenAI (default), with Ollama and Claude switchable in config
  - Embeddings: bge-small-en-v1.5 via FastEmbed (local)
  - Vector store: ChromaDB, plus BM25 keyword search and a reranker
  - UI: a simple web page for uploading documents, managing collections, and
    chatting with citations
  - Extras: Docker, tests that don't need a key, an evaluation script, and a
    README
